Bots

When to use it

Use it before you publish a new robots.txt, or when Search Console says a page is "Blocked by robots.txt" and you can't see why. Google's Search Console no longer has its own tester: its URL Inspection tool only checks the live file, one URL at a time, on a site you've verified. Nothing you paste here is sent anywhere.

How the decision is made

To find out whether robots.txt blocks a page, take the group of rules for the bot's name (or the User-agent: * group if it has none), find every Allow and Disallow line that matches the start of the URL's path, and the longest one wins. This page does that for you, for many URLs and bots at once, and shows the line that decided each answer.

These are the rules Google publishes for its crawlers, from RFC 9309 and Google's own robots.txt specification. Most other well-behaved bots, Bing's included, follow the same standard.

  1. One group per bot. A bot uses the group with its own name and ignores the rest. Only if there is no group with its name does it use User-agent: *. The two are never combined. So if you add a User-agent: Googlebot group, Googlebot stops reading your * rules: copy any you still want into its group.
  2. Some bots answer to two names. Googlebot-Image and Googlebot-Video use their own group if there is one, and the Googlebot group if not. Apple's Applebot does the same: with no User-agent: Applebot group, it follows your Googlebot group, not your * rules. So a Googlebot group also decides what Siri, Spotlight and Safari can find. Bingbot, with no group of its own, follows an old msnbot group before *.
  3. Groups with the same name are merged. Two User-agent: * groups in one file count as one.
  4. The longest matching rule wins. Allow: /shop/sale beats Disallow: /shop for /shop/sale/mugs, because it's longer. The order of the lines doesn't matter.
  5. A tie goes to Allow. If an Allow and a Disallow are the same length and both match, the page is allowed.
  6. No matching rule means allowed. An empty Disallow: blocks nothing.
  7. Paths are case-sensitive. Disallow: /Admin doesn't block /admin. The words User-agent, Disallow and the bot names aren't.
  8. Two wildcards. * matches any run of characters, and $ at the end means "the URL ends here". Disallow: /*.pdf$ blocks every PDF; Allow: /$ allows only the home page.

Mistakes this catches

  • A leftover Disallow: / from a staging site, a theme, a plugin or a "block search engines" setting. It blocks the whole site. (WordPress's "Discourage search engines" box no longer writes it: since version 5.3 it adds a noindex tag instead.)
  • Noindex: in robots.txt. Google ignores it. To keep a page out of search results, let it be crawled and put a noindex robots meta tag or X-Robots-Tag header on it. If robots.txt blocks the page, Google never sees the tag, and the URL can still be listed from links.
  • Crawl-delay:. Google ignores it. Some other crawlers read it.
  • Full URLs in rules. Disallow: https://yoursite.com/private matches nothing. Rules take the path only: Disallow: /private.
  • Relative sitemap addresses. Sitemap: needs the full address, starting with https://.
  • Misspelled fields like Disalow or Useragent. Google reads a few common ones anyway; other bots may skip the line.
  • Rules above the first User-agent, which belong to no group and are ignored.
  • A web page instead of a text file. Some servers answer /robots.txt with an HTML page. If it's a firewall's check page (“Just a moment...”), the tester says so: that page is what you got, not necessarily what Google got.

Where to change your robots.txt

Found a line to fix? Where you fix it depends on what your site is built with. On most site builders there's no file to upload: the builder writes robots.txt for you, from a settings screen.

  • WordPress. WordPress serves a robots.txt of its own until you add a real file. First look at Settings → Reading → Search engine visibility, and untick "Discourage search engines" if you didn't mean it. If the bad line is still there, an SEO plugin may be writing it: in Yoast it's under Yoast SEO → Tools → File editor (Yoast's guide), in Rank Math under General Settings → Edit robots.txt (Rank Math's guide), or a robots.txt file may sit in the site's top folder on your hosting, where your host's file manager can edit it.
  • Wix. In the dashboard, SEO & GEO, then Tools and settings, then Robots.txt Editor. "Reset to Default" puts back Wix's own file, which lets every bot crawl every page (Wix's guide).
  • Squarespace. You can't edit the file. Settings → Crawlers has a "Block search engine crawlers" box; when it's on, Squarespace adds Disallow: /. To hide one page, use "Hide page from search results" in that page's SEO settings instead (Squarespace's guide).
  • Shopify. Shopify writes a default file that suits most shops. To change it, go to Online Store, open the theme's menu, choose Edit code, and add a robots.txt.liquid template. Keep Shopify's default rules in it and add yours, because Shopify updates the defaults over time (Shopify's guide).
  • A site you upload yourself (plain hosting, Netlify, Cloudflare Pages, GitHub Pages). Robots.txt is a plain text file named exactly robots.txt in the top folder of the site, next to the home page's index.html. Edit it, upload it, then open yoursite.com/robots.txt to check the new version is the one being served.

Whichever it is, paste the changed file back in here before you save, and test the same URLs again.

If your site is behind Cloudflare

Cloudflare is a service that sits in front of many websites, often set up by whoever built the site. To check, look up your domain's nameservers on Google's dig page (pick NS). If they end in ns.cloudflare.com, your site is behind it, and three things can change what bots see:

  • Lines Cloudflare adds to your robots.txt. With its managed robots.txt switched on, Cloudflare puts its own block at the top of your file, between # BEGIN Cloudflare Managed content and # END Cloudflare Managed Content. It has a User-Agent: * group with Allow: /, then Disallow: / for AI training bots such as GPTBot, ClaudeBot, Google-Extended and CCBot. Search bots aren't on the list, but Google says Google-Extended also decides whether the Gemini apps use your pages in their answers, so this block can keep you out of those. You won't find these lines on your own site: they're switched on and off in the Cloudflare dashboard, under Security, then Settings, "Set your preference to block training in robots.txt".
  • A notice instead of "page not found". On sites with no robots.txt of their own, Cloudflare can serve a page of comments about "content signals". It has no rules, so it blocks nothing.
  • Blocks that robots.txt never shows. Under Security, Settings, "Configure AI bot policies", Cloudflare can turn away search, agent and training bots at the door, before your site sees them. Your robots.txt can allow a bot and the bot still gets nothing. Since 15 September 2026, newly added domains start with training and agent bots blocked on pages that show ads, and search bots allowed.

One side effect of the first one: Cloudflare's Allow: / and your own User-agent: * rules end up in the same group, and a tie goes to Allow. So a Disallow: / in your own * group no longer blocks the whole site, by Google's rules above. This page flags that when it sees it. Sources: Cloudflare's managed robots.txt and AI bot policies pages.

What robots.txt can't do

  • It controls crawling, not indexing. A blocked URL can still appear in Google, usually without a description, if other pages link to it.
  • It applies only to its own host. shop.yoursite.com needs its own robots.txt, and so does http:// if it's served separately from https://.
  • It's public, and it's a request. Polite bots follow it. Don't use it to hide private pages; put them behind a login.
  • After you change it, Google can take up to 24 hours to use the new file, because it caches the old one. In Search Console, the robots.txt report (Settings → robots.txt) shows the version Google has and lets you request a recrawl. Sources: robots.txt report, Google's crawler names.
